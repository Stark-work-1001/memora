# Operations

## Data directory

`MM_DATA` (or `--data`) selects it. Without either, Memory Merge uses the platform data directory:
`%LOCALAPPDATA%\memory-merge` (Windows), `~/Library/Application Support/memory-merge` (macOS),
`$XDG_DATA_HOME/memory-merge` or `~/.local/share/memory-merge` (Linux). Exception: if the 0.1 default
`<checkout>/data/memory.sqlite3` exists it keeps being used, so upgrading never presents an empty
store; `doctor` warns about it.

```text
memory.sqlite3        source of truth (WAL mode: -wal and -shm files appear while it is open)
markdown/<id>.md      derived, human-readable mirror (regenerated by `rebuild`)
markdown/inbox/       drop notes here; `sync` turns them into pending memories and removes the file
backups/              `backup` output and automatic pre-migration backups
```

Protect the directory with OS permissions and full-disk encryption. Exclude it from public repos
(the shipped `.gitignore` does).

## Health and diagnosis

```bash
memory-merge doctor            # environment, schema, integrity, backlog, backups, model config (no network)
memory-merge doctor --probe    # also sends one request to each configured model server
memory-merge health            # counts and integrity only
```

`doctor` returns `ok`, `warn` or `fail` per check with a hint. In-process model backends are not
loaded without `--probe`.

## Backup, restore and the restore drill

```bash
memory-merge backup                    # -> backups/memory-<timestamp>.sqlite3, integrity-checked
memory-merge backup /safe/place.sqlite3
memory-merge drill                     # backup -> restore into a temp dir -> compare every memory's id, digest, status, version
memory-merge restore BACKUP NEW_DIR    # never into an existing, non-empty directory
```

`backup` uses SQLite's online backup API, so it is safe while MCP servers are running, refuses to
overwrite a file, and reports `integrity_check` and the row count of the copy. `restore` copies a
backup into a new directory, migrates it if it is older than the code, rebuilds the derived index
and mirror, and verifies it. Switch over yourself: stop writers, point `MM_DATA` at the new
directory, restart the MCP hosts. `drill` proves the round trip on your real data and leaves no
files behind. Run it after changing machines or storage.

## Schema migrations

Opening a database migrates it automatically:

1. A database newer than the code is refused before anything is written (0.1 silently stamped its
   own version onto newer databases).
2. If the database holds data, a backup is written to `backups/pre-migration-vN-to-vM-<time>.sqlite3`
   and verified (integrity check and row count). If that fails, nothing is migrated.
3. All steps run in one `BEGIN IMMEDIATE` transaction; an error rolls back schema changes too.
4. The version is recorded in `PRAGMA user_version` and in the `meta` table. If an older Memory
   Merge reopens the database and stamps `user_version` down, the next open restores it and rebuilds
   the full-text index and vector table, because 0.1 can still run plain UPDATEs (reviews) that
   bypass index maintenance. 0.1 cannot insert into the 0.2 tables (column count differs): its
   captures fail loudly instead of writing half-formed rows.
5. `meta.history` lists every migration with its backup path.

Tests build real version-1 databases with the frozen 0.1 code (`tests/legacy/store_v0_1.py`,
byte-identical to the published file: SHA-256 `400e2f1a...921a`), migrate them, and compare every
row, the audit log, edges and the fresh-vs-migrated schema.

## Rebuilding derived state

```bash
memory-merge rebuild               # full-text index + Markdown mirror (0.1 rebuilt only the mirror)
memory-merge rebuild --fts-only
memory-merge rebuild --mirror-only
memory-merge index                 # embed memories lacking a vector for the configured model (incremental)
memory-merge prune-vectors --keep <fingerprint>   # after re-indexing with a new model
```

The full-text index is also rebuilt automatically when the analyzer version stored in `meta`
differs from the code's.

## Maintenance

```bash
memory-merge maintain              # integrity_check, FTS optimize, ANALYZE
memory-merge maintain --compact    # + WAL checkpoint(TRUNCATE) and VACUUM (close other processes first)
memory-merge report --project P    # never-recalled old memories, exact duplicates, unresolved contradictions (suggestions only)
```

## Forget and purge

| | `review ID forget` | `purge ID --yes` |
|---|---|---|
| Row | kept, status `deleted`, text retained | deleted |
| Full-text index, vectors | removed | removed |
| Judge advice | removed (if no live duplicate) | removed |
| Audit log | entry kept | entries kept, content digests nulled |
| Mirror file | removed | removed (retried until it succeeds) |
| Free pages, WAL | -- | zeroed (`secure_delete`), WAL truncated, VACUUM |
| Backups, snapshots, remote providers | untouched | untouched: reported, not handled |

Measured: after `purge`, a marker string occurs in no file of the data directory; with
`secure_delete` disabled the same purge leaves it in `memory.sqlite3`. If another process holds a
read snapshot the checkpoint is blocked and purge returns `complete: false` with a hint; close other
Memory Merge processes and run `maintain --compact`.

## Several processes on one database

Typical setup: one MCP server per agent host, the CLI, perhaps the viewer, all on one data
directory. SQLite arbitrates: writes take `BEGIN IMMEDIATE` with a 15 s busy timeout and surface as
`storage_busy` (retryable) if exceeded. Reads never wait for writers (WAL), and recall's access
statistics are best effort with a 0.2 s timeout, so a long import in one process does not stall
recall in another. The Markdown mirror is written under the same write lock as mutations, so an
older process cannot overwrite a newer version. The in-memory vector cache of a long-running server
is invalidated by a generation counter maintained by SQL triggers, so it notices changes made by
other processes.

There is no cross-machine synchronisation. Copying the data directory between machines while
servers run is unsafe; use `backup` and `restore`.

## Logging

Servers log to stderr (MCP stdio owns stdout) at `MM_LOG_LEVEL` (default `WARNING`). Migrations,
index heals and tool failures are logged; memory content never is.

## Upgrading from 0.1

1. `memory-merge backup` with the old version (or copy the data directory while nothing runs).
2. Install 0.2 and run `memory-merge doctor`. The first open migrates and writes its own verified
   backup.
3. Behaviour changes to know about:
   - `memory_remember(confirmed=True)` from an agent now queues for review unless
     `MM_TRUST_AGENT_CONFIRM=1`.
   - Identical content captured twice in a project is stored once; the second capture is
     recorded as a sighting (`support` counts distinct sources).
   - `rebuild` now also rebuilds the full-text index.
   - `tags` and `locator` are returned as JSON values, not JSON strings.
   - `memory_review_queue` returns `{items, next_cursor, calibration}` instead of a list.
   - Embedding vectors from 0.1 are kept under a `legacy-` fingerprint and never mixed into search;
     run `memory-merge index` to re-embed.
